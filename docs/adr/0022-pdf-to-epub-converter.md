# ADR 0022: PDF to EPUB conversion with an external converter

| | |
|---|---|
| **Status** | Accepted: shelf calls a converter the person installed; default recipe marker + pandoc (Markdown route); docling + pandoc documented as the alternative. Measured on `osx-arm64` only |
| **Date** | 2026-11-15 |
| **Scope** | PRD 6.16 (F-CNV-1 to F-CNV-4), 3.2 (non-goal "format conversion", now with one exception), 9.2 (Native AOT, no bundled converter), 9.4 (privacy: nothing goes online by itself) |
| **Roadmap** | M24 "PDF to EPUB" |
| **Inputs** | [ADR 0005](0005-epub-pdf-parsers-aot.md) (VersOne.Epub reads only), F-IMP-8 (`rclone` as an external tool), fixtures `derived/one-column.pdf`, `two-columns.pdf`, `footnotes.pdf` and `upstream/pdf/arxiv-2403.02174v1.pdf` |

## Context

A person wants to read a PDF on a Kindle. A fixed page layout is hard to read on a small screen; a reflowable EPUB is not. The EPUB can be sent to the Kindle directly (Send to Kindle takes EPUB), so no MOBI or AZW3 step is needed. PDFs with two columns and footnotes must keep their reading order; scanned PDFs are out of scope (no OCR, PRD 3.2).

Owner decisions taken before the work:

- **External tool**, like `rclone` (F-IMP-8): shelf bundles no converter and the binary stays one Native AOT file (G7).
- **Calibre is not a candidate** (too large an installation).
- **Two columns are in scope.**
- The test PDFs are generated by `tests/Shelf.TestData` (no third-party content), plus the CC0 arXiv paper already in the fixtures.

## Options

- **A. Calibre `ebook-convert`**: rejected by the owner.
- **B. pandoc alone**: pandoc does not read PDF.
- **C. docling** (MIT) to Markdown, then pandoc to EPUB 3.
- **D. marker** (`marker-pdf`) to Markdown, then pandoc to EPUB 3.
- **E. MinerU**: not measured (AGPL, very heavy installation); kept as a fallback if C and D fail on real books.
- **F. Own converter on PdfPig** (text and font sizes to paragraphs and chapters, own EPUB writer): no external dependency, but the reading order of columns and footnotes would be our own heuristic.

## Measurements (`osx-arm64`, tools installed with `uv tool install`, pandoc and epubcheck from Homebrew)

| Input | Route | Result |
|---|---|---|
| `arxiv-2403.02174v1.pdf` (7 pages, one column, formulas) | docling → **HTML** → pandoc | `epubcheck` error: `nav.xhtml` has an empty `ol` (the table of contents has no entry) |
| same | docling → **Markdown** → pandoc | valid (0 errors, 0 warnings), 6 headings kept |
| same | marker → Markdown → pandoc | valid; headings kept; formulas as inline LaTeX, pandoc reports a parse error for `\cal` |
| `two-columns.pdf` | docling → Markdown → pandoc | valid; left column before right column |
| `two-columns.pdf` | marker → Markdown → pandoc | valid; left column before right column |
| a page with a footnote at the foot of the page | docling | the footnote lands **between** the two columns |
| same | marker | the footnote lands **after** the main text |

Time (observation, not a gate): docling 27 s for 7 pages including the first model download; marker 8 s for the same file.

## Decision

1. shelf runs the command of `convert.command`, a template with `{input}` and `{output}`. The command is the person's own and runs only on `shelf convert` (F-CNV-2).
2. **Default recipe:** marker for the layout, pandoc for the EPUB, through the **Markdown** route. The HTML route of docling is not used. docling + pandoc stays documented as the alternative.
3. The recipe is a small wrapper script that shelf documents but does not install, because one template line cannot hold two steps cleanly.
4. shelf checks the result itself (valid zip, readable OPF, at least one chapter with text) and adds nothing if the check fails (F-CNV-2). It does not run `epubcheck` (Java).

## Consequences

- **Formulas stay weak.** Both tools write LaTeX; a Kindle shows MathML poorly. Mathematical PDFs convert, but the formulas may be unreadable. Not fixed here.
- **License.** marker's code is GPL-3 and its model weights have their own license (free for personal use, limits for commercial use). shelf only starts it as a separate process; the person installs it. docling is MIT.
- **Heavy installation for the person**, not for shelf: PyTorch and models, several GB, downloaded on first use (docling and marker go online for the models once; shelf itself does not).
- **Not measured:** real books (hundreds of pages), scanned PDFs (refused before the call), `linux-x64`, three or more columns, footnotes that sit in the text flow.
- **Risk:** both tools change quickly; the recipe is configuration, so a better tool replaces it without a change in shelf.
- The generator of `tests/Shelf.TestData` gained `PdfColumnPage` (positioned columns and footnotes) and three derived fixtures (`one-column.pdf`, `two-columns.pdf`, `footnotes.pdf`).
